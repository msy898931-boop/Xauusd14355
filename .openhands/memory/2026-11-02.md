## ⭐ biquote serves OHLC, not just a spot quote
`GET https://biquote.io/api/{symbol}/ohlc?interval=<tf>&limit=<1-1000>&from=&to=`
- `interval` ∈ {1m,5m,15m,30m,1h,4h,1d}. `limit` default 100, max 1000.
- Response `{"symbol","interval","bars":[{openTime,open,high,low,close,volume,tickVolume,isOpen}]}`,
  **newest bar first**, current bar tagged `isOpen:true`.
- `volume` is ALWAYS 0 (broker CFD, same trap as the tick) → use `tickVolume`.
- `x-robots-tag: noindex, nofollow` on the OHLC response.

**Depth is a retention ceiling, NOT the `limit`.** Raising `limit` past 1000 does
nothing, and `from`/`to` do **not** page deeper — they only *trim*. Measured max
bars per timeframe (2026-11-02):

| tf | bars | from → to |
|----|-----:|-----------|
| 1m | 301 | 11:45 → 16:45 same day (~5h) |
| 5m | 289 | 30 Oct 14:45 → now |
| 15m | 193 | 29 Oct 13:45 → now |
| 30m | 193 | 27 Oct 11:30 → now |
| 1h | 169 | 22 Oct 08:00 → now |
| 4h | 181 | 22 Sep 16:00 → now |
| 1d | 500 | 25 Mar 2025 → now |

So "كل الشمعات المتاحة" = ~5h of M1, ~4d of M5, ~6d of M15/M30, ~11d of H1,
~6w of H4, ~19mo of D1. The MT5 broker store is the limit; there is no deeper page.

## MarketDesk — the multi-agent desk (second build this day)
Owner asked for an agent-based market+news analyst: several agents, each with a
specialty + private memory + a shared memory that holds the biquote data source;
the orchestrator is central management. Built at **`/workspace/project/marketdesk/`**

**Shape:** `orchestrator.gather()` pulls all biquote candles + quote into

weights signed scores, applies the risk gate, builds the plan. Each agent =
one craft, one weight, a private `AgentMemory` JSON, and a `Study` published to
the shared `studies` table. Add an agent = subclass + one line in `ROSTER`.

**The 8:** structure (2.0) · trend (2.0) · levels (1.5) · news (1.5) ·
momentum (1.2) · risk gate (fail-closed) · volatility (0.8) · correlation (0.7).

**Two things worth remembering:**
1. **⭐ Groq rejects urllib's default UA with 403 `error code: 1010`** (Cloudflare).
   A browser-like User-Agent is REQUIRED — same wall as Kraken/gold-api/FF. This
   is why the first full run silently fell back to deterministic text: the LLM
   returned None and the agents narrated themselves. `llm.py` now sets the UA.
2. The **risk agent runs BEFORE synthesis and can veto** — `allowed=False` forces
   `no-trade` regardless of the weighted score. Fail-closed, never softened.

**Invariants enforced in code + tests:** every level tagged `pivot`/`fib`/
`projection`; an uncomputable metric is `None` never `0`; a source failure is
`[]` not an all-clear; the model narrates but cannot add a number.

### ⭐ Bug found on the first real "حلل" run — the gate was disarmed by a race
The first full analysis returned `allowed: True` while the news agent's own study
said `event_risk_24h: True` — the gate contradicted the evidence on the same
board. Cause: all 8 agents ran in ONE ThreadPoolExecutor. The risk agent reads
the shared SQLite **instantly**; the news agent waits on the **network**. So the
gate always won the race and read an empty `studies` row → waved through the
high-impact event it exists to block. A silent fail-OPEN in a fail-closed gate —
the worst kind, because the output looked fine.
Fix: `dispatch()` runs the **news agent FIRST, alone**, then the other 7 in the
pool. Owner's spec actually said this ("tell the news agent to gather + analyse
and send back" before the rest) — I had parallelised it away. Regression test
`test_news_runs_before_risk_gate` (20 tests now). Also made the no-trade note
name the exact reason instead of "either/or".
**Lesson:** when one agent's output is another's input, concurrency is a
correctness bug, not just a speed knob. Draw the dependency edge and serialise it.

### Audit pass — four real defects, each found by measurement not inspection
The owner asked "what is missing for this to be excellent". Instead of listing
generic advice I audited the code and *measured* each claim.

**1. Indicators were fed the FORMING bar.** `frames_data()` returned every row
including the newest bar, which is still open — its h/l/c move with the tick, so

the partial bar vs 30.8 without (Δ 7.2)**; 1h RSI 59.8 vs 65.1. Enough to flip a
reading. The `is_open` flag was already stored and carried into the reshaped bar
but **no consumer ever read it**. Fix: `frames_data()` filters `not r["is_open"]`;

**2. The neutral band was hardcoded 0.15 in 13 places** (orchestrator, every

**3. The news comparison was unfair.** `keyword = classify(title + description)`

### Running `serve` — and the one thing the agent cannot fix
`serve` is running in the background: `nohup python3 -u -m desk.cli serve
--interval 15 > data/serve.log 2>&1 &` (pid changes each restart; find with
`pgrep -f "desk.cli serve"`). The log gets one JSON line per pass:
`{"run_id":…, "verdict":"no-trade", "score":-0.129, "alerted":false,
"reason":"no directional call"}`.
**Secrets must be passed on the SAME command line that starts the process.**
`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` are injected by the harness into the
command's environment; a later command does not see them. Verified with
`tr '\0' '\n' < /proc/$PID/environ | grep -c TELEGRAM_BOT_TOKEN=`.
**`TELEGRAM_BOT_TOKEN` in this environment is INVALID: `getMe` returns 401
Unauthorized.** So alerts cannot be delivered until the owner sets a real token —
`Notifier.available` is True (both strings are non-empty) but `send()` returns
False. The desk stays silent, which is the designed behaviour, but the owner
would wrongly think alerting works. **Do not confuse "configured" with "working":
`available` only checks the strings are non-empty.** A `getMe` probe is the only
honest check, and it costs one API call.
- To rotate the token: Telegram → @BotFather → `/token` (or `/newbot`).
- To get the chat id: message the bot, then read `getUpdates`.

### check-alerts: the silence was ambiguous
The desk is silent by design, so **"not configured" and "no signal yet" looked
identical from outside** — there was no way to answer "are my alerts working?"

### ⭐ Telegram token: the update never reaches the sandbox (proved by fingerprint)
Owner said "updated" **twice**. Each time: `TELEGRAM_BOT_TOKEN` fingerprint is
**0c9f76d8** — byte-identical, unchanged across ~4 hours, and identical to the
value the session started with at 16:36. Proof it is not a propagation delay:
same fingerprint in the oldest serve process (`/proc/16245/environ`), in a fresh
command injection, and via raw `curl` (`getMe` → 401). Shape is perfect
(46 chars, 2 segments, all printable ASCII, 27 distinct chars in the secret) —
**a well-formed dead token**, so shape checks prove nothing.
**Leading hypothesis: the sandbox's environment is bound at creation.** The
harness may inject secrets from a snapshot taken when the sandbox/conversation
starts, so a secret edited mid-session never appears. Remedy to try: set the
secret **first**, then start a **new conversation** (fresh sandbox).
**Transferable method: to prove a secret did NOT change without printing it,
compare a fingerprint (sha256[:8]) of the value in a fresh command against the
value in a long-running process's `/proc/<pid>/environ`.** Equal fingerprints =
same value = the update did not land. This is the honest way to answer "did my
secret update take effect?" when you must not echo the value.
Also probed alternate names (`TELEGRAM_TOKEN`, `BOT_TOKEN`, `*_NEW`) — all unset,
so it is not a naming mismatch inside the sandbox.

## ⭐⭐⭐ The backtest: the desk's own answer is "no proven edge" (PR #10)
Built `desk backtest` (walks the stored daily bars, real agents, real grading).
**Two bugs found while building it, both "a number that looked earned":**

1. ⭐⭐ **Look-ahead in the backtest itself.** `save_candles` upserts and never
   deletes, so a reused store keeps bars from *after* the decision bar. First
   version reused the package store → the trend agent saw **all 500 bars at
   every step** and called **"bear" 379/379 times** on a market that **rose
   18%**. It printed 306 trades, **every one a short**, at a "significant"
   **+0.23R**. Fix: fresh temp store per walk + a guard that raises when the
   newest bar is not the decision bar. **Look-ahead does not announce itself —
   it produces a beautiful, significant, wrong answer.** Tell: an all-one-
   direction book, and a direction hit rate *below* 50% while expectancy is
   positive (the profit came only from the R skew).
2. ⭐ **The stop's ATR came from `frames["1h"]` only.** No 1h frame (daily-only
   walk, or an agent restricted coarser) → `None` → stop silently became **1% of
   price**. Now the frame is chosen from what the volatility agent reported, the
   frame is recorded as `atr_frame`, and a plan with no measured ATR carries a
   warning.

## ⭐⭐⭐⭐ The decisive finding: the desk's direction adds NOTHING
Chased "why is direction 55% but expectancy 0?". The answer was not the stop or
the entry — it was that **there was never a method to begin with.**

Built controls that replay each of the desk's own decisions with the direction
replaced (same entry, same risk distance, same bars):

```
desk direction        +0.371R
always short          +0.374R      <- the same number
always long           -0.279R
desk minus always-short  -0.003R  t=-0.02  95% CI [-0.249,+0.244]
```

**The desk == "always short".** Why: it was short on **60% of a window in which
gold rose 18%** (73% of the sample was the fall). A constant short bias harvests
the crash; the agents add nothing separable. Regime split confirms it — a
constant wins in **all three thirds** (rise, peak, fall). And a **two-line
EMA20/EMA50 rule scores +0.315R vs the desk's +0.371R**: eight agents and 25
files are not clearly paying for themselves.

### ⭐⭐ The methodological lesson (the big one)
**A positive expectancy on one sample is not an edge.** Any result must be
printed next to (a) the constant-direction control, (b) the regime split, (c) a
trivial benchmark. Otherwise a regime is read as skill. This is the fifth time
on this desk that **the number, not the code, was lying** — and the first time
the number was *mine*. Also: my first analysis pass measured MFE over the whole
window *even after the stop was hit*, which flattered every exit rule; a proper
bar-by-bar replay with the stop checked first is what made the numbers honest.

### Two like-for-like errors I made and fixed
* Controls first compared all trades (unresolved counted as 0R) against a replay
  marked to market. Now resolved trades only.
* Default grading horizon was 10 bars → most trades decided by the stop. Now 20

**Where the desk stands: clean, honest, reproducible, and with no demonstrated

## The desk as one always-on process (daemon + Docker)

The user asked: how do I keep Telegram on all the time, never sleeping, with
real-time market events? The honest answer had two halves and they are not the
same thing: **"the bot never sleeps"** (answer a press in ~1s) and **"events are
instant"** (a level alert the moment price touches it). They have different
ceilings, and only the first is really about hosting.

**Why the two-loop shape existed.** On GitHub Actions the desk *had* to be two
loops that never spoke: `serve` read the market on an interval but not the chat;
`bot --listen` read the chat for a few minutes but not the market. A runner is a
fresh VM every time, so nothing can stay resident — that is not a design flaw,
it is the platform. The bot was only *awake* ~33% of the time (200s per 5 min),
so a press could wait ~3 minutes. On a real host the two-loop shape is just wrong.

**The fix is one process, three cadences** (`desk/daemon.py`, `desk daemon`):
chat long-polled continuously (~1s reply), levels every 10s, a full reading
every 15m. Lessons that cost real thought:

- ⭐ **"Always-on" and "instant" are different promises; do not let one borrow the
  other's credibility.** The feed is *polled HTTP* (`biquote.fetch_quote`), not a
  stream, so the finest honest cadence is the level interval. Anyone promising
  tick-instant alerts on a polled feed is lying. Say the ceiling out loud.
- ⭐ **The market closes, so "never sleeps" has a hole in it.** Gold is shut from
  Friday 21:00 UTC to Sunday 22:00 UTC — ~1/7 of the week. The daemon stands the
  *market* jobs down but keeps serving the chat. Reading a frozen tape is the
  failure this avoids, not a limitation to apologise for.
- ⭐ **A daemon that dies is worse than one that misses a tick.** Every job is
  caught: a failed level check does not stop the reading; a rejected token backs
  off and reports instead of killing the process. Verified live — the junk
  `TELEGRAM_BOT_TOKEN` produced `{"job":"bot","error":"RuntimeError"}` repeatedly
  while the readings kept running and the process exited 0.
- ⭐ **Cadence clocks must start at `-inf`, not 0.** With `last_level=0.0` the very
  first tick ran *nothing* (monotonic time is large), so a fresh process sat idle
  for a full interval. A one-line bug that a "does it work" smoke run catches and
  a unit test written against the happy path would not.
- ⭐ **A vague `stats: dict[str, object]` is where mypy earns its keep.** The dict
  form made every counter read an `object`; mypy flagged 8 real errors that the
  tests passed straight through. Replaced with explicit typed fields
  (`self.ticks: int`, `self.alerts: list[str]`). Same lesson as the earlier
  `summary` dict-vs-string bug: **annotate the state, not just the signatures.**
- **A container needs a volume at `DESK_HOME`, or it re-sends what it already
  sent.** The alert ledger and SQLite store live there. Without a mount, every
  restart forgets the dedupe record. Documented in the Dockerfile, the README,
  and `render.yaml` — three places, because losing it is silent.
- **Render free tier has no worker and no disk.** A web service sleeps ~15 min;
  a long poll is outbound and would not count as activity anyway. The always-on
  shape is a paid worker (~$7/mo) or a small VPS; the free fallback is the
  15-minute cron, kept in `render.yaml` as the second service.

Verified end to end: image built (180MB, non-root uid 10001), ran with a volume,
produced a full reading + auto-graded the scoreboard, exited 0 on `--seconds`.
Gates: 155 tests, mypy clean (36 files), ruff clean, both YAMLs parse.

## The inbound endpoint: why "always-on free" needed a webhook, not a web page

The user asked whether moving the desk to a web page would let it run free
forever. The question hides the real variable: **a "web page" is not what makes
hosting free — INBOUND traffic is.** A static page is free everywhere but serves
files, not a desk; the backend behind it has the same problem either way. The
honest reframing: what keeps a free host awake is a request ARRIVING.

- ⭐ **A free web host sleeps on the absence of INBOUND traffic, and a long poll
  is entirely OUTBOUND.** So polling would never wake a sleeping host -- and the
  host sleeping would freeze the very loop doing the polling. This is why the
  desk's `serve` shape could never be free-and-awake: it was structurally
  invisible to the sleep heuristic. An endpoint fixes both at once: Telegram's
  push is inbound, and so is a plain uptime ping to `/health`.
- ⭐ **The two Telegram transports are mutually exclusive.** `getUpdates` is
  refused while a webhook is set, so `--web` is a MODE, not an addition. A
  "just also add a webhook" change would silently break the poll.
- ⭐ **One reply path, or two clients that drift.** `handle_update` was extracted
  from `poll` and is now called by BOTH the poll and the webhook. A webhook that
  answered differently would be a second, silently diverging chat client, and the
  divergence would only ever show up in production, one update at a time. Same
  lesson as the neutral band in 13 places and the currency map: **one rule, one
  implementation.**
- ⭐ **A forged POST must be rejected BEFORE an action, not by the chat check.**
  The chat-id guard only stops a stranger's request from spending a quota; it
  still runs the endpoint's code. Telegram echoes a `secret_token` back in a
  header, so the endpoint checks it in constant time (`hmac.compare_digest` --
  a byte-by-byte compare leaks the token) and returns 403 before anything else.
- ⭐ **A bad update must answer 200, not 5xx.** A non-2xx makes Telegram REDELIVER
  the same update, so a bug in one action becomes a retry storm. The failure is
  reported in the JSON body instead. The 200 IS the acknowledgement; there is no
  offset to confirm.
- ⭐ **"Configured" is not "working", again.** I wrote `DESK_LEVEL_EVERY` into
  `render.yaml` while the CLI only read the flag -- the config promised a cadence
  the process never used. Caught it by reading my own blueprint against the code.

## Level alerts: watch what the desk actually said, not a typed list

The user asked me to add a Telegram alert on the scenario levels I had just given
them (3,919.49 breakdown, 3,937.51 breakout). Reading the code first paid off:
`watch_once` ALREADY watched the desk's own last plan (`from_recommendation` --
entry, stop, first target), and only fell back to the hand-typed `DEFAULT_LEVELS`
when there was no plan. So "add an alert" was half done already.

The real gap: the watcher read the PLAN but not the SCENARIOS. Those name
different prices -- the breakout/breakdown triggers, i.e. what happens if the
plan never fills.

- ⭐ **A desk that says "no trade" still prints scenarios.** So a plan-only
  watcher goes silent exactly when the market is deciding something -- the moment
  the trader most wants to hear. The scenario triggers are precisely the levels
  that matter when there is no plan to watch.
- ⭐ **Measure the cost before deciding it is too expensive.** I nearly rejected
  watching scenarios because the level check runs every ~10s and building them
  looked heavy. Measured: **5 ms**, read-only over shared memory, no agent, no
  model. The cost was never the reason to skip it. (Same discipline as the
  budget and the closed-bar fix: the number, not the intuition.)
- ⭐ **Two sources naming the same shelf is noise, not emphasis.** The plan and
  the scenarios can name one price from two angles; the watched set is their
  UNION deduped by price, first-wins so the plan's more specific label survives.
- **A switch for every behaviour change that adds noise.** `DESK_WATCH_SCENARIOS=0`
  restores plan-only. An operator who finds the extra alerts noisy must be able
  to silence them without a code change.
- ⭐ **A token embedded in a git remote expires, and `git push` then blocks on a
  password prompt** (not a clean failure -- it hangs). Fix: re-point the remote
  with the CURRENT token from the environment,
  `git remote set-url origin https://x-access-token:${GITHUB_TOKEN}@github.com/...`.
  The commit was already safe locally; only the push was stuck.
- **The `--web`/scenario work all landed**: 170 tests, mypy clean (37 files),
  ruff clean. Live `desk levels` now reports `crossed 1 of 6 levels` = the plan's
  3 plus the scenarios' 3.

## The Render blueprint was wrong, and only a budget test could catch it

The user asked "is the Render way free or does it cost money?" — and checking
found a real bug in `render.yaml` that would have *broken the deployment*, not
just cost a dollar.

- ⭐ **Render's 750 free instance-hours are per WORKSPACE, shared across every
  free service — not 750 each.** Do the arithmetic before adding a service:
  one always-on service = 30-31 x 24 = **720-744 h**. A second free service
  running even 20 h lands the workspace at **764 h > 750**, and Render suspends
  **every** free service in the workspace until the next month. The blueprint had
  a 15-min cron as a "belt-and-braces" second opinion — it was the exact failure
  it was meant to guard against.
- **Render Cron Jobs have NO free instance type** (~$1/mo minimum, prorated by
  the second). Only web services and static sites are free. So the cron was also
  the one paid thing in a "free" blueprint.
- ⭐ **A blueprint that parses is not a blueprint that works.** The YAML was
  valid; the *resource budget* was not. Validate the arithmetic (hours,
  bandwidth, service count), not just the syntax.
- ⭐ **A failure that is a suspension, not an exception, needs a test or it never
  shows up.** No run would ever go red for this. Added
  `test_render_blueprint_stays_inside_the_free_hour_budget` (asserts ONE service,
  plan free, `/health`, every secret `sync: false`) and
  `test_the_keepawake_workflow_pings_health_within_the_sleep_window`.
- ⭐ **A GitHub Actions cron ping replaces an external uptime service for free.**
  `/health` every 5 min on a public repo = inbound traffic, so a free Render
  instance never sleeps. No UptimeRobot account, no second dashboard, and the
  ping lives next to the code it keeps awake. 5 min against a 15-min sleep window
  gives three chances, so one late/skipped run does not let it sleep.
- **Render Hobby bandwidth dropped 100 GB → 5 GB/month (Apr 2026).** Measured
  need here: reads (15 min) + level checks (30 s) + pings ≈ **0.6 GB/month**.
  Not close, but it is the cap that suspends the service if a loop ever runs.
- **marketdesk is NOT deployed to Render.** No `marketdesk*.onrender.com` exists
  anywhere in the repo or its history; the only Render deployments in memory are
  `analysisdesk` and an unrelated `goldbot`. `render.yaml` existing ≠ deployed —
  the same "configured ≠ working" lesson, this time on a whole service.

## Probing the live bot: "is it running all the time?" found four real faults

The owner asked for a health check on the bot, assuming it had been running
non-stop. It had not. Checking the *outside* (Render URLs, Actions API, CI
status) rather than reading the code is what found these.

- ⭐ **GitHub's `schedule` is best-effort, and on this repo it was near-dead.**
  A `*/5` cron produced **2 scheduled runs in ~17 hours**, while every
  `workflow_dispatch` succeeded. Docs: runs are delayed under load and "some
  queued jobs may be dropped"; `:00` is the single most congested slot and moving
  off it is the *only* knob GitHub offers. So the bot was **not** answering
  presses every 5 minutes. Fix: offset the cron (`2-59/5`, `3-59/5`, `7-59/15`).
  **This does not make cron reliable** — it removes the one avoidable cause. If a
  hard cadence is ever needed, an external scheduler calling `workflow_dispatch`
  is the only reliable pattern.
- ⭐ **My own guard tests broke CI, and green locally hid it.** The two tests I
  added imported `pyyaml`, which was never a dependency; CI installs `.[dev]` and
  the module was simply absent. Locally pyyaml happened to be present → 172 green.
  **Verify a dependency change in a CLEAN venv** (`python3 -m venv`), because that
  is the only thing that reproduces CI's world. `pyyaml` is now in `[dev]`.
- ⭐ **A live service's name is a fact you have to look up.** The keepawake ping
  defaulted to `marketdesk-daemon` (what the blueprint *would* name it), but the
  real service was created by hand as `marketdesk`. `-daemon` → **404
  (`x-render-routing: no-server`)**. The check would have warned forever without
  saying why.
- ⭐ **`x-render-routing` in the response headers tells you the real state.**
  `suspend-by-user` → the service is suspended by its owner (503 "This service has
  been suspended by its owner"); `no-server` → no such service. Two different
  failures that both look like "not working"; the header names the actual one.
- **The bot does work when it runs.** A scheduled pass logged
  `{"ok": true, "handled": ["help" x7], "listened_s": 202.0, "next_offset": ...}`
  — the token in repo secrets is valid (the env one here is junk), and the
  long-poll answered 7 presses. The gap was *cadence*, not the bot.
- **A workflow committed after the last cron tick has never run.** keepawake
  showed 0 runs; its first ping was simply still ahead of it. "No runs yet" ≠
  "broken" — check the commit time against the schedule.
- ⭐ **A dropped cron tick is indistinguishable from a healthy one.** Nothing goes
  red; the schedule fires and the run is silently skipped. Only comparing
  `created_at` against the expected slots in the Actions API shows it. Same family
  as the suspension bug: **the failure is an absence, not an error.**

## The webhook and the poller fight over one transport (2026-11-03, evening)

The owner pasted the Render dashboard: the **live** service is `Xauusd14355-4`
(live, Free, Docker, https://xauusd14355-4.onrender.com), **not** the
`marketdesk-daemon` the blueprint names and **not** the `marketdesk` I found
suspended earlier. Three names, one real service. Probe, never assume.

- ⭐ **Telegram serves updates to a webhook OR to getUpdates -- never both.**
  The Render daemon registers a webhook on boot (`_start_webhook` → `set_webhook`),
  so the Actions poller got a bare `getUpdates HTTP 409` on every run and the
  workflow went **red**. The message read like a broken token; it was a transport
  conflict. A bare status code is not a diagnosis. Now: the 409 message names the
  conflict, `desk telegram` reports the real transport via `getWebhookInfo`, and
  the workflow treats a 409 as a *notice* (the daemon owns the transport, which is
  the better setup) so a healthy deployment stops looking broken.
- ⭐ **`getWebhookInfo` is the only honest answer to "why does the bot not
  answer?"** Live output: `{"url": "https://xauusd14355-4.onrender.com/telegram",
  "pending_updates": 0, "last_error": null, "transport": "webhook"}`. It also
  surfaces a stale URL or a rejected secret, which is otherwise invisible.
- ⭐ **A blueprint name is what the deploy CREATES, not a label.** `render.yaml`
  said `marketdesk-daemon` while the live service is `Xauusd14355-4`. Syncing the
  blueprint would have created a **second** free service -- the exact 750-hour
  breach the file's own header warns about. Renamed to match.
- **Render auto-names a hand-created service `<repo>-<n>`** (`Xauusd14355-4`), and
  the `-4` is a suffix from name collisions, not a count of live services. Only
  `-4` answered; `-1..-3` were 000/501 (cold start), `-5` was 404.
- **A 501 right after a cold start is transient** -- the next request was 200.
  Retry before concluding a service is down.
- The keepawake ping had **never run** (committed after the last cron tick). First
  manual run: `GET .../health -> 200`, "the desk is awake". "No runs yet" ≠ broken.
